# 第 21 次运行：GitHub 公开发布与复现闸门

## 1. 本次完成了什么

- 增加 GitHub Actions：自动运行单元测试、160 条随机测试数据闭环和公开内容审计。
- 增加公开发布审计脚本与机器可读审计结果。
- 增加 GitHub 发布准备清单，明确发布前必须人工完成的事项。
- 保持 Materials Project 正式数据、网页索引证据、随机测试数据和本地敏感文件之间的边界。
- 首次按 README 原命令试跑时发现：全新环境未设置 `src` 导入路径，8 个测试模块中 4 个导入失败；已将 README 与 CI 统一修正为显式 `PYTHONPATH=src`，随后重新验证。这一过程保留为可解释的复现失败路径。

## 2. 对原有设计的落实与调整

- 落实“GitHub 是 PDF 的证据附件”：仓库能自动证明最小闭环可运行。
- 落实“单一正式数据源”：自动检查没有引入第二个科研数据源。
- 落实“严禁敏感信息进入上传仓库”：本地目录继续忽略，并新增扫描闸门。
- 新增约束：曾在聊天或界面暴露的 API 密钥必须在公开上传前轮换。理由是目录隔离不能撤销既往暴露风险。
- 未上传 GitHub、未生成二维码、未改冻结的第一大点；缺少真实仓库地址和团队信息时不制造占位证据。

## 3. 对应初赛文稿哪些部分

- §2.3：日志、固定随机种子、预算状态和自动运行记录。
- §3.2：同一环境中的 Random、Static Top-N、Iterative 可复现比较。
- §3.3：测试失败或公开审计失败时阻止发布，形成明确失败判定。
- §4.1：一条命令完成最小试跑。
- §4.2：凭据泄露、数据混用和错误晋级被列为风险并设置阻断。
- §4.3：依赖、运行入口、CI、日志、开源边界和发布流程形成实物证据。

## 4. 接下来讨论、设计与落地什么

1. 确认公开 GitHub 仓库名称、所有者和团队署名。
2. 在公开上传前轮换 Materials Project API 密钥。
3. 在可联网环境跑通官方 API，并回填正式队列状态。
4. 仓库发布后生成真实二维码，加入 PDF 第 4 页。
5. 按组委会正式模板和团队信息制作最终提交版，而非继续扩展技术栈。
